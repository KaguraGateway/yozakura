> **プロジェクト名**: yozakura
> **リポジトリ**: `yozakura`
> **アプリ名(暫定)**: yozakura / 夜桜 / よざくら
>
> **名前の由来**: 夜に静かに咲く桜。一人で自分と向き合う時間、夜に自分を整える時間、というアプリの哲学を体現。

## 0. このプロダクトの本質

最初のアイデアは「AI生活管理&ジムトレーニングアプリ」(秘書機能、タスク管理、Duolingo的ゲーム性、メモ機能などを含む全部入り構想)でした。

ユーザーへのヒアリング(ブランコ問題回避のため)を通じて、本当に欲しいものは以下だと判明しました。

- **ゴール**: 3ヶ月後にジムに継続して通えていて、体が変わっている状態
- **最大の障害**: 「行く気にならない」(疲れて動けない)
- **障害の正体**: 漠然とした疲労ではなく、構造的な2つの問題
  1. 回復を考慮しないメニュー設計 → 筋肉痛で次回サボる
  2. ジム前日の予定が無防備 → 飲み会の翌朝行けない

このため、**ジム継続に絞ったアプリ + 拡張余地を残す**設計に着地しました。秘書機能やタスク管理は「将来拡張案」として保留。

## 1. プロダクト概要

| 項目 | 内容 |
|---|---|
| 目的 | 週3回のジム通いを継続し、3ヶ月後に体が変わっている状態を作る |
| ユーザー | 自分一人(ADHD傾向、ジム前日の予定と筋肉痛で挫折しがち、初心者) |
| トレーニング目的 | 姿勢改善・体力向上・健康維持(筋肥大バキバキではない) |
| コアバリュー | 「行く気にならない」を、メニュー最適化と前日防衛で構造的に解決 |
| 設計思想 | Duolingo的ゲーム性ではなく、疲れた現実に寄り添う設計。崩れた時に責めず、淡々と巻き返しを提案する |

## 2. 機能スコープ

### Phase 1: 土台

1. **トレーニングログ**: 種目・重量・レップ・セット・日付を記録
2. **成長グラフ**: 種目別の重量推移を可視化
3. **記録モードの中断機能**: 体調不良などで途中で終わる時の保存

### Phase 2: 本丸

4. **回復前提のメニュー提案**: 次回トレ日と前回ログから、今日のメニューを生成
5. **マシン待ち回避**: 種目の後回し・代替提案・順番入れ替え

### Phase 3: 防衛機能

6. **ジム前日アラート**: Googleカレンダー連携で、前日に飲み会等を検知し警告
7. **リカバリー提案**: 崩れた週の巻き返しプラン提案

### 将来拡張案(今回は作らない、案として保持)

- 生活管理・ADHD向けタスク管理
- ジム以外も含む秘書機能
- クイックメモ
- ゲーミフィケーション(継続率が伸びなかった時の打ち手として)
- HealthKit連携(睡眠時間・活動量を取り込んで体調判定を補強)

Google OAuthのリフレッシュトークンはサーバーのSecretに焼き付ければ、以降自動更新で動作。

## 4. メニュー提案ロジック設計

### アーキテクチャ: ハイブリッド構成(ルール + LLM)

**役割分担**

```
┌──────────────────────────────────────────┐
│ ルール側(Go)                              │
│  ・前回ログから次回の重量・レップを計算  │
│  ・規定レップ達成判定、デロード判定      │
│  ・基本のローテーション(A/B交互)         │
├──────────────────────────────────────────┤
│ LLM                                      │
│  ・種目選択と順番                        │
│  ・体調(好調/普通/疲れ)への対応          │
│  ・代替種目の状況依存提案                │
│  ・リカバリープラン                      │
│  ・励まし・フィードバックの文言生成      │
└──────────────────────────────────────────┘
```

**重要な原則**: 重量・レップの数値計算は絶対にLLMに任せない。健康被害に直結するため。LLMは種目選択係、ルールは数値担当。

### トレーニング設計の方針

ユーザーが初心者であることを踏まえた設計:

- **週3回 × 全身トレーニング A/B 交互**(分割なし)
- **マシン中心**(エニタイム想定、フリーウェイトより安全・待ち時間短い)
- **コンパウンド種目中心**(プレス、プル、スクワット系)
- **Linear Progression**: 前回全達成 → 次回+2.5kg(下半身+5kg)、未達 → 据え置き、2回連続未達 → -10%デロード
- **1回あたり45〜60分**、種目数は5〜7程度

### メニュー生成フロー

```
[朝7時 k8s CronJob] 当日分のメニュー生成
  ↓
  ┌─ ルール側で準備 ─────────────────────────┐
  │ 1. 直近メニュー履歴を取得                │
  │ 2. 各種目の「次回推奨数値」を計算        │
  │ 3. 前回がA/Bどちら? → 次は反対側         │
  └──────────────────────────────────────────┘
  ↓
  ┌─ LLM呼び出し ─────────────────────────────┐
  │ 入力:                                    │
  │  - 今日の調子(好調/普通/疲れ)            │
  │  - 直近メニュー履歴(過去2週間)           │
  │  - 推奨ベース(A or B)                    │
  │  - 種目マスタ(動作パターン付き)          │
  │  - 推奨重量・レップ(ルール側計算済)      │
  │ 出力: 種目リスト(順序付き)               │
  └──────────────────────────────────────────┘
  ↓
[DBに当日メニューを保存]
  ↓
[ホーム画面表示時] キャッシュから即座に表示
  ↓
[必要時に再生成] 体調変更時、マシン待ち時など
```

### LLMへの「調子」効かせ方の指針

| 調子 | LLMへの指示方針 |
|---|---|
| 好調 | 推奨ベース通り。新種目を試す提案もOK |
| 普通 | 推奨ベース通り。種目数は標準 |
| 疲れ | 種目数を1〜2減らす / 高負荷種目(レッグプレス等)を後回しか省略 / 軽めの種目に置換 |

重量・レップはルール側固定なので、LLMが勝手に数値を弄ることはない。

### 種目マスタ

20〜30種目で初期データを用意。以下の属性を持つ。

- 種目名
- 主働筋(胸/背中/肩/脚/腕/体幹)
- 動作パターン(プレス / プル / スクワット / ヒンジ / 補助種目)
- 推奨重量刻み(マシンによって異なる、例: バーベル2.5kg、マシン5kg)
- 代替種目グループ(同じ動作パターンで置換可能)
- LLM向け説明文(「初心者向け基本種目」「フリーウェイト」など)

**初期データ例**

- 胸: マシンチェストプレス、ペックフライ
- 背中: ラットプルダウン、シーテッドロウ、マシンロウ
- 肩: マシンショルダープレス、サイドレイズ(ダンベル)
- 脚: レッグプレス、レッグエクステンション、レッグカール、ヒップアブダクション
- 腕: ケーブルカール、トライセプスプレスダウン
- 体幹: アブドミナルマシン、バックエクステンション

## 5. 画面設計

### 全体構成

3タブ構成で確定。**画面を増やさない**ことが重要(ジム中の操作時間を最小化するため)。

```
┌─────────────────────────────────────┐
│         (アクティブ画面)            │
├─────────────────────────────────────┤
│  [今日]    [履歴]    [グラフ]       │
└─────────────────────────────────────┘
```

### タブ1: 今日(ホーム)

**通常時の表示要素**

- 次のジム予定(Googleカレンダー連携 or 固定スケジュール)
- 前夜の警告(Phase 3、飲み会等を検知)
- 今日の調子タップ(好調/普通/疲れ)→ 変更時にメニュー再生成
- 今日のメニュー(朝7時バッチ生成済み)
- トレーニング開始ボタン(最大・最目立つ位置)
- 今週の状況(X/3回完了、ニュートラルに表示。Duolingo的ストリークは出さない)

**休息日の表示**

- 「今日は休息日です」と明示(サボってる日ではないことを伝える)
- 次のジム予定 + 想定メニュー

**崩れた時(Phase 3)**

- 「火曜のセッションをスキップしました」のリカバリー提案
- LLMが文言生成。**責める言葉を使わない**ことをプロンプトで明示

### タブ1から遷移: 記録モード(最重要画面)

このアプリで一番長く触る画面。1セットごとに開くため累積接触時間が最長。UXは最優先。

**画面構成**

```
┌─────────────────────────────────────┐
│ ← 上半身プル                        │
│                                     │
│ [チェストプレス▼] [ロウ] [カール]   │ ← 種目チップ(横スクロール)
│  ━━━━━━━                              │   現在の種目は強調
│                                     │
│ 前回: 47.5kg × 10, 10, 8            │
│ 目標: 50kg × 10 × 3                 │
│                                     │
│ Set 1  ✓  50kg × 10                 │
│ Set 2  ✓  50kg × 10                 │
│ ─────────────────────────────       │
│ Set 3                               │
│                                     │
│      kg: [- 50 +]   [-- ++]         │
│     rep: [- 10 +]                   │
│                                     │
│         [✓ セット完了]              │
│                                     │
│  ⏱  レスト 01:23                    │
│                                     │
│         [次の種目へ →]              │
└─────────────────────────────────────┘
```

**操作仕様**

| 項目 | 仕様 |
|---|---|
| 数値入力 | ±ボタンで前回値から調整。種目ごとに刻み幅をマスタ管理(2段階刻み: ±標準刻み と ±大きい刻み) |
| セット完了 | ✓ボタン明示タップ。完了後、次セット欄に同値を初期表示 |
| レストタイマー | セット完了時から自動カウントアップ |
| 種目遷移 | 上部の種目チップ(タップで切替 / 長押しで並べ替え)+ 下部「次の種目へ」ボタン |
| マシン待ち回避 | 種目を後回し / 代替種目提案 / 順番入れ替え |
| 中断機能 | 「中断」ボタンで途中保存、メニュー提案ロジックも認識 |
| 完了時 | 総時間と総ボリューム(kg×reps×set)のサマリー表示 |

**初期値設計**: 前回の同セット番号の数値を入れる。前回と同じならタップ1回で記録完了。

### タブ2: 履歴

日付逆順のリスト。各エントリをタップで詳細展開、ここから誤入力修正も可能。

- スクロールで過去に遡れる
- カレンダー表示モード(月単位、Phase 1では省略可)
- 個別ログの編集

### タブ3: グラフ

家でゆっくり振り返る画面。ジム中には開かない前提なので、情報量を増やせる。

**表示要素**

- 今週のサマリー(ジム回数、総ボリューム、先週比)
- 種目別の重量推移(メインのグラフ、Phase 1必須)
- 部位別の頻度(直近30日、バランス確認用)

**Phase 1 MVPでは「種目別の重量推移」だけから始める**。サマリーと部位別頻度は後追加。

### 削った/置かない画面(意図的)

- 設定画面 → Phase 3で初登場
- メニュー編集画面 → 記録モード上で変更可能
- 種目マスタ管理画面 → 新種目は記録時にその場で追加
- プロフィール/目標設定 → 「週3回」が暗黙にあるだけで十分
- 通知設定画面 → Phase 3で必要になってから

## 6. 重要な設計判断のログ(あえて削ったもの・選ばなかったもの)

### Duolingo的ゲーミフィケーションを外した

ユーザーの挫折原因が「連続記録切れ」ではなく「筋肉痛と飲み会」だから。連続記録ゲームでは効かない。むしろストリーク表示は崩れた時に罪悪感を増幅させるため、意図的に出さない。

### 秘書機能・タスク管理・メモを後回しにした

ゴールが「ジム継続→体が変わる」に絞られているため、まずジム機能を完成させて使う習慣を作る。週末ペースで全部入りを目指すと挫折確実。

### ユーザー認証を最小化した

一人用 + ネットワーク層(Tailscale/Cloudflare Tunnel)で絞れば、アプリレイヤの認証は不要。将来人にも使わせたい時に足せばいい。

### k8s採用は既習技術として(学習用途ではない)

業務で慣れているため、自宅サーバーで使うのは自然な選択。マイクロサービス化の余地もあり、将来拡張(秘書機能等)を横に並べやすい。

### 画面を3タブに絞った

ジムでスマホ操作する時間は短いほどいい。タブを増やすほど、結局自分が使わなくなる。

### 記録モードを最重要画面と位置づけた

1セットごとに開くため、累積接触時間が最も長い。ここのUXを最優先。

### ルールベース + LLMのハイブリッドを採用

LLM単独だと:
- ハルシネーションが怪我に直結(具体的な重量数字を間違えられない)
- 進歩の追跡が不安定になる
- コストとレイテンシの問題

ルール単独だと:
- 体調や状況への柔軟対応ができない
- 励ましの文言が機械的になる

役割を分けることで、両者のいいとこ取りを狙う。

### メニュー生成は朝7時バッチ + 必要時再生成

- ホーム開いた瞬間にメニュー表示済み(レイテンシゼロ)
- k8s CronJobで動かすのが綺麗にハマる
- バッチ失敗してもジムに行く夕方までに気付ける

ただし、ジムでの体調変更やマシン待ち時は同期API呼び出しで再生成。

### LLMはインターフェース抽象化で選定を遅延

Claude / OpenAI / Gemini / ローカルLLM、どれにするかは他の設計が固まってから判断する方が後悔しない。Goの`MenuPlanner` interfaceで抽象化しておく。

### 初心者向けに「回復前提」より「Linear Progression」を優先

最初は「日曜ハード → 火曜筋肉痛で詰む」という挫折パターンを「回復前提のメニュー設計」で解こうとしていたが、ヒアリングで初心者と判明。初心者ならそもそも適切な負荷設定(全身週3、軽めから漸進)で問題が消える。「回復前提のメニュー」は中級者以上の課題。

### 7-8. k8sマニフェストとTerraform構成

## 9. このアプリの北極星

迷ったらここに戻る。

> **「疲れて動けない自分」を、責めるのではなく、構造的に支えるアプリ**

- 連続記録を煽らない
- 完璧を求めない
- 崩れた時のリカバリーを優しく提案する
- ジム中の操作は最小限のタップで終わる
- 数字(重量・レップ)は嘘をつかない
- 「行く気にならない」を前提にした設計

これに反する機能追加は、たとえ便利でも入れない。
